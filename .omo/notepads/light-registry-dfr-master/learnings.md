## Todo 1: Create alembic migration 008_device_registry.py

**Date:** 2026-07-05

### SQLAlchemy 2.0 breaking change: `postgresql_where` on `UniqueConstraint`
- **Finding**: SQLAlchemy 2.0 no longer accepts `postgresql_where` on `sa.UniqueConstraint`.
- **Error**: `Argument 'postgresql_where' is not accepted by dialect 'postgresql' on behalf of <class 'sqlalchemy.sql.schema.UniqueConstraint'>`
- **Fix**: Implement partial unique constraints as `unique=True` indexes with `postgresql_where` via `op.create_index(..., unique=True, postgresql_where=sa.text("..."))`.
- **Impact**: `get_unique_constraints()` does NOT return these; they appear in `get_indexes()` with `unique=True`.

### Inspector caching pitfall
- **Finding**: `sqlalchemy.inspect(engine).get_table_names()` caches results across calls within the same inspector instance.
- **Symptom**: `test_idempotency_downgrade_upgrade` falsely reported table missing after upgrade because the inspector cached the pre-upgrade table list.
- **Fix**: Use raw SQL (`SELECT 1 FROM pg_tables`) or create a fresh inspector for each existence check.

### `sa.Identity()` vs `SERIAL`
- **Finding**: `sa.Identity()` generates `GENERATED BY DEFAULT AS IDENTITY` (Postgres 10+ standard), not legacy `SERIAL`.
- **Result**: `\d device_registry` shows `generated by default as identity` for `device_id` — functionally equivalent to SERIAL but modern.

### Migration structure
- File: `Infrastructure/automation-service/alembic/versions/008_device_registry.py`
- down_revision: `007_pid_per_room`
- Uses `op.create_table`, `op.create_index`, `op.drop_table`, `op.drop_index`
- Dialect guard: `if op.get_context().dialect.name != "postgresql": raise NotImplementedError`

## Todo 2: Pydantic domain models (Device, LightDevice, LightDeviceCreate, LightDeviceUpdate)

**Date:** 2026-07-05

### What was built
- `app/models/device_registry.py` created with four Pydantic v2 models:
  - `Device` — generic non-light base (heaters, fans, etc.)
  - `LightDevice` — light-specific with DFR0971 dimming fields, relay binding, per-room index
  - `LightDeviceCreate` — request body for creating a light on an empty DFR slot
  - `LightDeviceUpdate` — request body for renaming/moving/binding a light

### Validation constraints implemented
- `device_type`: `Literal["light"]` on `LightDevice`, `str` on `Device`
- `cluster`: `Literal["main"]` on both (rejects `front`/`back` per cluster topology contract)
- `board_id`: `Field(ge=0)` (DFR board IDs are 0, 1, 2)
- `dimming_channel`: `Field(ge=0, le=1)` (DFR has 2 channels per board)
- `per_room_index`: `Field(ge=1)` (1-based index within room)
- `device_name`: `Field(pattern=r"^light_[fvlo]_\d+$")` (canonical naming)
- `dimming_enabled` defaults to `True`, `dimming_type` defaults to `"dfr0971"`, `safety_level` defaults to `0`

### config_schema.py changes
- `DeviceConfig` kept with `# DEPRECATED` comment pointing to new models (backward compatibility for YAML bootstrap)
- `AppConfig.devices` narrowed from `Any | None = None` to `dict | None = None` (still optional for YAML-bootstrap path where devices block is absent)

### Test strategy (TDD)
- Wrote `tests/test_device_models.py` FIRST — it failed with `ModuleNotFoundError` before models existed
- 20 tests covering: valid construction, rejection of invalid dimming_channel/cluster/device_type/board_id/per_room_index/device_name, defaults, all room prefixes, create/update request bodies
- All 20 tests pass; full suite (124 tests) passes with no regressions

### Verification
- pyright: 0 errors, 0 warnings on both `device_registry.py` and `config_schema.py`
- Python import: `from app.models.device_registry import LightDevice, Device, LightDeviceCreate, LightDeviceUpdate` succeeds
- Evidence captured in `.omo/evidence/task-2-light-registry-dfr-master.txt`

### Key decisions
- `LightDevice` and `Device` are separate models (not inheritance) because they have different field shapes — `Device` has required `channel` (relay), `LightDevice` has optional `relay_channel` and DFR-specific fields
- `dimming_board: str | None` on old `DeviceConfig` was NOT ported to new models — new model uses `board_id: int` per inherited wisdom (YAML already uses `dimming_board_id: int`)
- No runtime code modified (ConfigLoader, routes, etc.) per todo boundary

### JSONB serialization with asyncpg
- **Finding**: asyncpg 0.31.0 requires JSONB values to be passed as JSON strings with explicit `::jsonb` cast in SQL.
- **Error**: `asyncpg.exceptions.DataError: invalid input for query argument $N: [] (expected str, got list)`
- **Fix**: Use `json.dumps([])` / `json.dumps({})` for `interlock_with` and `pid_setpoints` parameters, and add `::jsonb` casts in INSERT/UPDATE SQL.
- **Migration impact**: SQLAlchemy + psycopg2 also requires `json.dumps()` for JSONB bound parameters; raw Python dicts/lists cause `psycopg2.ProgrammingError: can't adapt type 'dict'`.

### LightDevice model extension
- Added `device_id: int | None = None` field to `LightDevice` so repository methods can return the primary key alongside domain fields.
- `_row_to_light_device()` helper maps DB row dicts to `LightDevice` instances, including `device_id`.

### Migration 009_seed_device_registry_from_yaml
- Reads `automation_config.yaml` devices block and seeds `device_registry` idempotently.
- Applies `_canonicalize_device_types` inline (`heater` → `heating`).
- For lights: derives `per_room_index` from `light_N` suffix, generates `device_name` as `light_{prefix}_{N}`.
- For non-lights: uses YAML key as `device_name`.
- All inserts use `ON CONFLICT (location, cluster, device_name) DO NOTHING`.
- Downgrade: `DELETE FROM device_registry`.
- Seeds 13 devices total (6 lights + 7 non-lights).

### Test architecture

- `TestSeedMigration`: 3 sync alembic integration tests (subprocess) verifying seed count and idempotency.
- Both test classes have `setup_class` managing alembic state to avoid cross-test contamination.

## Todo 4: Light CRUD endpoints, root-cause #1 fix, I2C lock, CASCADE, tests

**Date:** 2026-07-05

- `app/repositories/devices.py` extended:
  - `get_light_by_id(device_id)` — fetch light by PK
  - `cascade_device_name_change(old_name, new_name, location, cluster, redis_client)` — updates `effective_setpoints` rows and renames Redis keys in a transaction
- `app/models/device_registry.py` — added `safety_level` to `LightDeviceUpdate`
- `app/routes/routes.py` — added dependency override for `lights.get_device_repo`

### Root-cause #1 fix
- Previously `DELETE /api/devices/channels/{ch}` deleted the light from YAML config entirely
- New behavior: if the device on that channel is a light, `clear_relay_binding_only(device_id)` NULLs the `channel` field in `device_registry` but preserves the row
- The light survives; only the relay binding is cleared

### I2C lock pattern
- Module-level `_i2c_bus_1_lock = asyncio.Lock()` in `app/hardware/i2c_lock.py`
- `acquire_i2c_bus_1()` returns the same lock instance to all callers
- Test endpoint checks `if i2c_lock.locked(): raise HTTPException(409)` before entering `async with i2c_lock:`
- Control loop's `HardwareBatchExecutor` can acquire the same lock in a follow-up

### CASCADE implementation
- DB update wrapped in `asyncpg` transaction: `UPDATE effective_setpoints SET device_name = $1 WHERE location = $2 AND cluster = $3 AND device_name = $4`
- Redis: scans `effective_setpoint:{loc}:{cluster}:light:{old_name}:*` and renames keys; also renames `light:{loc}:{cluster}:{old_name}`

- `test_relay_clear_nulls_only.py`: 3 async route tests verifying root-cause #1 fix (light survives with NULL channel)
- `test_dfr_test_button.py`: 5 async route tests for DFR sweep endpoint including failsafe block, I2C busy, sweep sequence, state restore, and unbound-light path
