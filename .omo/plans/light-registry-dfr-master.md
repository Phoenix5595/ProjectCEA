**What you'll get:** All your devices — lights, heaters, fans, dehumidifiers — move out of a YAML config file (that gets overwritten on every deploy) into the database (which survives deploys). Lights become first-class citizens born on the DFR dimmer panel: you assign a light to a room, give it a display name and a number, and it then shows up in the relay dropdown filtered by room. Lights already wired to another relay are greyed out (one relay per light, enforced by the database). Each DFR channel gets a Test button that sweeps the light 100%→10%→100% over 5 seconds so you can physically identify which light is which — the control loop is told to stand down during the test, and prior state is always restored even if something goes wrong. Two bugs you hit get fixed: (1) clearing a relay no longer deletes the light from the DFR panel (it only unbinds the relay, the light survives), and (2) deploying no longer resets your device config (because devices now live in the database, not in the deploy-overwritten YAML file).

**Why this approach:** You were explicit — "I do not want to have to edit the YAML all the time when playing with devices." The repo was already halfway to a database-backed device model (device_states + device_mappings + a DeviceRepository already existed); the YAML `devices:` block was the last non-database piece, and the deploy script was rsync-overwriting it from git on every release. Completing the database migration finishes the job the repo already started and eliminates the deploy-reset bug by construction. The typed-domain refactor (Deploy 4) is the long-term-solid end-state you wanted; it ships as the final pure-refactor wave after the feature is stable, with characterization tests pinning current behavior first so the crop-safety control loop doesn't regress.

**What it will NOT do:** Will not touch the YAML hardware/sensors/control sections (only `devices:` moves to DB). Will not add new Redis keys for device identity. Will not change the cluster topology contract (main=devices, front/back=sensors). Will not make the internal device_name a free-text field (it is system-generated as `light_v_1`, `light_f_2`, etc. — only display_name is free-text). Will not break the control loop tick (1-5s) or use `time.sleep` in the loop. Will not bundle unrelated modernize-device-access scope beyond Deploy 4's typed-domain replacement.

## Scope
### Must have
- All device identity moves from `automation_config.yaml` `devices:` block into a new `device_registry` Postgres table (lights + heaters/fans/dehumidifiers/etc).
- `config.get_devices()` reads from `device_registry` (via DeviceRepository) instead of YAML; returns the SAME `{location:{cluster:{device_name:{...}}}}` dict shape so the control loop's 12 call sites need zero change until Deploy 4.
- YAML `devices:` block becomes first-run-bootstrap only: on startup, if `device_registry` is empty, seed from `automation_config.yaml` ONCE (idempotent). After first boot, `devices:` is ignored for identity (hardware/sensors/control sections remain YAML).
- DFR0971 panel is the master create/edit surface for lights: empty (board, channel) slot shows "Add light"; occupied slot shows editable display_name/room/per_room_index + Test button + Remove light.
- Per-room light index: stored, user-editable, conflict-checked; auto-suggested as (max existing index in that room + 1).
- device_name convention: `light_{room_prefix}_{per_room_index}` (e.g. `light_v_1` = Veg Light #1, `light_f_2` = Flower Light #2). System-generated, deterministic. Regenerates when room or index changes — cascades update to schedules, control_history, device_states, device_mappings, Redis keys (`light:{loc}:{cluster}:{device}` etc), effective_setpoints. display_name is the only human free-text field.
- Relay channel-assignment dropdown: when device_type=light + location selected, options = lights from `device_registry` WHERE room=selected_location; lights already bound to another relay channel are DISABLED (greyed out). Strict relay↔light 1:1 invariant enforced at DB level (UNIQUE on relay channel for lights).
- `clear_channel_device` (devices.py:638-672) REWRITTEN: for lights, NULLs only the `channel` field on the registry row (preserving the DFR binding + identity — root-cause #1 fix); for non-lights, preserves existing delete-row behavior for now.
- DFR test button: 5-second sweep 100%→10%→100%. Hard interlock: bus-wide asyncio.Lock (no concurrent DFR test); device forced to `manual` mode during test (scheduler + PID skip it); relay held ON (dimming a powered-off LED driver is invisible); prior intensity + prior mode restored in `finally` (even on failure/timeout); 30-second deadman cap as a fail-safe; blocked entirely if the room is in a failsafe state.
- UNIQUE(board_id, dimming_channel) constraint on `device_registry` (preserves existing DFR global-uniqueness invariant, currently enforced in code at lights.py:280-296).
- Pydantic `Device` + `LightDevice` domain models (`app/models/device_registry.py`) for API contracts + runtime type safety.
- Preserve Pydantic config validation (config_schema.py) for the YAML bootstrap; add validation for new DB-backed rows.
- TDD throughout (>80% coverage, repo rule). Every behavior pinned with pytest BEFORE implementation.

### Must NOT have (guardrails, anti-slop, scope boundaries)
- Will NOT touch the YAML `hardware:`, `sensors:`, `control:` sections — only `devices:` moves to DB. Hardware I2C config, sensor mappings, PID/safety limits, update_interval stay YAML-deployed.
- Will NOT bundle unrelated modernize-device-access scope beyond Deploy 4's typed-domain replacement.
- Will NOT add new Redis keys for device identity — DB is now the source; existing per-light Redis telemetry keys (`effective_setpoint:...:light:{device}:*`) are preserved (the device_name cascade updates them in place).
- Will NOT change cluster topology contract: `main` is the only device-cluster; `front`/`back` are Flower sensor sub-clusters only and never hold light devices.
- Will NOT make `device_name` a human free-text field — it is system-generated from (device_type, room, per_room_index). display_name is the only free-text field.
- Will NOT change the control loop tick (1-5s), Redis operations (<1ms), or break the `EngineConfigCache` 30s TTL amortization.
- Will NOT skip the bus-wide lock for the test button (only one DFR sweep in flight at a time across all 3 boards).
- Will NOT use raw `time.sleep()` in the control loop — the test sweep runs as an async task with `await asyncio.sleep` and yields control between intensity steps.
- Deploy 1 ships nothing user-visible. Deploy 2 eliminates deploy-reset. Deploy 3 ships the feature. Deploy 4 is pure refactor. No prod half-state between deploys.
