# settings-relay-matrix-dfr-cleanup - Work Plan

## TL;DR (For humans)

**What you'll get:** The relay matrix on the Devices page will show real "ON since 2m" / "IDLE since 5m" timestamps for every relay — including ones cycled by the automation's hysteresis logic (heaters, fans chattering near setpoint), which currently change state silently with zero record. The manual timer countdown ("ON 5m", ON 10m, etc.) will survive browser refresh, tab close, and multi-tab use because the timer lives in the database, not in the browser's memory. The Settings tab will show the YAML configuration panel (it's already wired, just never deployed). The DFR dimmer section will show its two channels side-by-side per board instead of stacked. The relay matrix will be tighter — dropping the "16-CH Relay Module" header, terminal strip decorations, and the colored vertical glyph bar that duplicated the LED dot's information. PID parameters (Kp/Ki/Kd) and the binary hysteresis band will be editable PER-ROOM in each room's automation tab — Flower Room's heater Kp will no longer be shared with Veg Room's heater Kp, and the hysteresis band in ON/OFF mode will also be per-room (no restart required: changing the band takes effect within ~5s as the control loop re-reads).

**Why this approach:** You called it twice — `control_history` is already the table that should be the single source of truth for state changes, and the existing `/api/hardware/relays/state` endpoint already returns per-channel `timestamps` (via `get_last_changed_per_channel()`) that the frontend already polls every 5s. The missing piece was that `_log_control_action` (the method that writes to control_history) computed `new_state` from `control_output > 0.5` instead of reading the ACTUAL relay state — so when hysteresis kept the relay in the same state but control_output crossed 0.5, it logged a SPURIOUS transition, corrupting the timestamps. Fix: make `_log_control_action` read the actual relay state after the control is applied (so `log_control_action`'s `old_state == new_state` short-circuit works correctly), and add one nullable column (`manual_expires_at`) for the timed-manual case only, with a partial index for the auto-expiry sweep. On the PID side, you were also right twice: PID parameters today are stored globally per device_type (one Kp for ALL heaters — Flower + Veg share it), which is wrong because the rooms have different thermal mass and heater capacity. Same for the binary hysteresis band. Fix: alembic migration adds location+cluster+binary_hysteresis columns to the pid_parameters table (the PK changes from `device_type` to `(location, cluster, device_type)`); PidRepository + StateManager + PIDControllerManager all fetch and cache per-room (with default-values fallback for missing rows); PID routes accept per-room URL paths; VerticalPIDBlock threads location/cluster from ZoneConfig and edits per-room values. Frontend deletes all three of its ad-hoc timer implementations (in-memory map in DeviceManager, the localStorage timer in ManualLightControl) and derives everything from the already-polled device data (ZoneConfig's `relayTimestamps` pattern was already correct and stays). No new Redis keys (existing `pid:parameters` key just gets location+cluster in its shape), no new device_states columns, no new endpoints, no new abstraction layer — the DB is already the authority for the manual+engine PID paths; this fixes the logging accuracy and makes the per-room shape real.

**What it will NOT do:** It will not add new Redis keys for device state (control_history DB table is the single source of truth). It will not add columns to the device_states table. It will not refactor the state-change call shape into a new unified method — existing paths stay as they are, just with logging added. It will not touch the DFR board square aspect or rename field (you only asked for channels side-by-side). It will not change the compact relay matrix variant (ZoneConfig's matrix works fine, only the panel variant on Devices page loses chrome). It will not use manual `systemctl restart` — both deploys run via `./deploy.sh`. It will NOT bundle the two safety-critical paths into one atomic deploy — deploy 1 (todo 17) ships state-change tracking + frontend cleanup, verifies green, then deploy 2 (todo 18) layers per-room PID + hysteresis on top. If deploy 2 breaks, deploy 1's improvements remain in production.

**Effort:** Large — 18 todos across 7 waves (3 deploy phases: code waves 1-3 → deploy 1 → verify → deploy 2). Two alembic migrations, per-room PID storage reshape, state-change tracking unification, frontend timer-impl deletion, matrix/DFR cleanup, per-room hysteresis.
**Risk:** Medium (down from Medium-High thanks to the two-deploy split) — each safety-critical path (state-change tracking vs. PID parameter resolution) now deploys and verifies in isolation. If either fails, deploy.sh auto-reverts ONLY that phase; the other remains live. The per-room PID migration still preserves backward compat for legacy global rows during the deploy window via the fallback in todo 12.
**Decisions to sanity-check:** (1) auto-expiry sweep runs every control-loop tick (1-5s) — fine for now since manual timers are rare and the partial index (`WHERE manual_expires_at IS NOT NULL AND mode = 'manual'`) keeps the scan cheap; revisit if it shows up in loop latency profiling. (2) hysteresis state changes now log accurately to control_history — `log_control_action` short-circuits on `old_state == new_state` so only actual transitions are logged (no in-band-output false positives after todo 2's fix). (3) ManualLightControl's "all lights 5m" use case maps to per-device manual_expires_at (each light gets its own expiry); no need for a zone-level timer concept. (4) Per-room binary_hysteresis uses default-values fallback (kp/ki/kd/binary_hysteresis defaults) when a per-room row is missing — NOT a `location IS NULL` fallback (which is dead code after migration 007 backfills all rows). (5) VerticalPIDBlock device_type values ('heater'/'fan'/'co2') vs YAML device_type values ('heating'/'cooling'/'co2') — the new `get_binary_hysteresis` must normalize so the lookup matches whatever convention the pid_parameters table actually uses; **VERIFY with `psql -c "SELECT DISTINCT device_type FROM pid_parameters"` before writing the normalization logic — the direction depends on what's actually in the table.** (6) SystemSettingsPanel's global "Binary Hysteresis" Tuning field is labeled "(deprecated)" after deploy 2 — it remains as the DB-failure fallback value loaded into `PIDControllerManager.__init__`, but per-room is the authority. (7) deploy.sh does NOT run alembic — the service runs `run_alembic_migrations()` on startup and catches exceptions; a failed migration logs a warning but does NOT fail the health check, so verify migrations applied via `psql \d` after deploy, not via deploy.sh logs.

## Commit strategy
Atomic commits per code-change todo (16 commits for todos 1-16) + 2 deploy commits (todo 17 commits todos 1-10's work, todo 18 commits todos 11-16's work). Total ~18 commits. Each todo's Commit line specifies the conventional-commit message. Order: todos 1-16 land on the working branch (waves 1-3, can be in any order within their wave); todo 17 commits the state-change tracking + frontend cleanup work + runs ./deploy.sh (deploy 1 of 2); after todo 17 verified green, todos 11-16 commit + todo 18 runs ./deploy.sh (deploy 2 of 2). Ruff runs once per deploy phase (per Cursor rule, deploy.sh also runs Ruff at start as a safety net). 

**Two-deploy split rationale:** this plan touches two safety-critical paths in the control loop (state-change tracking + auto-expiry sweep, AND the PID parameter resolution the control loop depends on per-tick). Bundling them in one atomic deploy means if either breaks, deploy.sh auto-reverts BOTH and you cannot isolate which one failed. With two deploys: deploy 1 verifies state-change tracking + frontend cleanup in isolation; if it breaks, you fix forward at deploy 1 and deploy 2 hasn't run yet. Deploy 2 then layers per-room PID on top of verified-green state. If deploy 2 breaks, deploy-1 state remains live (you keep the matrix timestamps, SystemSettingsPanel, etc.) and you can fix forward on per-room PID without losing deploy-1 improvements.

If either deploy fails health check and auto-rolls back, the commits remain in git — do NOT revert them; investigate (journalctl -u automation-service) and fix forward with a new commit + new deploy of the failing phase only.
